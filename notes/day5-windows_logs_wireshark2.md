# Day 5 — Windows Logs & Wireshark Investigation

## Objective

The objective of this investigation was to examine Windows Security logs and network traffic using Wireshark, identify useful evidence, and understand how host-based and network-based evidence can complement each other.

---

# 1. Windows Event Viewer Investigation

## Initial Understanding

Before investigating the Security log, I expected it to contain information such as:

* Successful logons
* Failed logon attempts
* Account-related activity
* Logoffs
* Attempts to access security-sensitive resources
* Other security-related system activity

Security updates and patches may also be recorded in Windows logs, but they are not necessarily recorded as Security logon events. Different Windows logs record different types of system activity.

---

## Event ID 4624 — Successful Logon

### Event Selected

**Date/Time:** 02-09-2026 19:02
**Account:** `Jeevitha$`
**Computer:** `JEEVITHA`
**Logon Type:** `5`

### What does Logon Type 5 mean?

Logon Type **5 means Service**.

It indicates that a service or a process running as a service has logged on using an account. This is different from an interactive user logging into Windows directly.

The `$` at the end of `Jeevitha$` can indicate that the account is being represented as a machine/computer account in a Windows context. Therefore, this event should not automatically be interpreted as me manually entering my password and logging into the desktop.

### Evidence Observed

* The account involved was `Jeevitha$`.
* The computer involved was `JEEVITHA`.
* The Logon Type was `5`, indicating a service logon.
* There was no IP address or source network address provided for this event.
* The Network Information section did not contain a remote network address.
* Process information, including a Process ID and process name, was provided.
* The event was generated as part of Windows Security Auditing.
* The process information appeared to be associated with the system rather than a remote machine.

### Initial Interpretation

The event appears to represent **service-related authentication/activity on the local Windows system**, rather than a direct remote login.

The absence of a source IP address and remote network information makes a remote login less likely from this particular event.

However, the event should not be considered suspicious or benign based on one field alone. Other events, process information, account details, and timestamps would need to be correlated before reaching a conclusion.

### What would make this more suspicious?

I would investigate further if:

* A privileged or unexpected account was involved.
* There were multiple failed logons followed by a successful logon.
* The account was not normally expected to perform the activity.
* The process associated with the event had a suspicious executable path.
* The activity occurred at an unusual time or in an unusual sequence.
* There was evidence of remote access.
* The service or process was unfamiliar or unexpected.

A successful logon by itself is **not evidence of an attack**.

### Observation

There were no useful failed-logon events available on my machine during this investigation.

Therefore, I did not create or assume a failed-login scenario.

### Investigation Question

If a suspicious account had several failed logons followed by a successful logon, I would investigate:

* Which account was being targeted?
* Where were the attempts coming from?
* What type of logon was being attempted?
* Why did the attempts fail?
* Was the successful logon performed by the same account?
* Did any process execute immediately afterward?
* Was there evidence of remote access?

This would allow the failed and successful events to be investigated as a sequence rather than as isolated events.

# 6. TCP Investigation

I used Wireshark to examine TCP traffic.

I identified the TCP three-way handshake:

```text
SYN
↓
SYN-ACK
↓
ACK
```

### Understanding

* **SYN** is used to initiate the TCP connection.
* **SYN-ACK** acknowledges the request and indicates that the server is willing to establish the connection.
* **ACK** completes the three-way handshake.

After the handshake is completed, the client and server can exchange application data.

### Investigation Question

> What does the three-way handshake tell an investigator?

It provides evidence that a TCP connection was being established between the two endpoints.

---

# 7. TLS / HTTPS Investigation

After TCP establishes the connection, additional traffic is exchanged between the client and server.

For an HTTPS website, the communication uses TLS encryption.

I could see traffic identified as **Encrypted Application Data**.

### Observation

I could not simply read the webpage contents from the encrypted application data.

This demonstrates the difference between HTTP and HTTPS:

* HTTP transmits application data without TLS encryption.
* HTTPS uses TLS to encrypt the application data.

Even though the contents are encrypted, some information about the communication can still be observed, such as:

* Source and destination IP addresses
* Ports
* Packet sizes
* Timing
* Protocol information
* TLS-related information

### Investigation Question

> If the application data is encrypted, what information can still be useful to a network investigator?

# 8. ARP Investigation

I also examined ARP traffic.

I observed an address such as:

`192.168.x.x`

and my device's MAC address was involved.

### What is ARP used for?

ARP is used on a local network to determine the **MAC address associated with an IPv4 address**.

For example, a device may know the local IP address it wants to communicate with but need to determine the corresponding MAC address before sending the Ethernet frame.

### Investigation Questions

* Which IPv4 address is being resolved?
* Which MAC address responds?
* Is the device on the local network?
* Why does the device need the MAC address?

ARP operates at the **Data Link layer (Layer 2)**, while DNS is generally considered an **Application layer (Layer 7)** protocol.

# 10. Host vs Network Evidence

## What Windows provides

Windows Event Viewer provides host-level information such as:

* User/account activity
* Successful logons
* Failed logons
* Process creation
* Process IDs
* Process names
* System activity
* Authentication-related information
* Potential administrative activity

This allows an investigator to understand **what was happening on the computer itself**.

## What Wireshark provides

Wireshark provides network-level information such as:

* Source and destination addresses
* Protocols
* Ports
* Packets
* DNS queries
* TCP connections
* TLS traffic
* ARP activity
* Timing and packet-level information

This allows an investigator to understand **what was happening over the network**.

---

# 11. Host and Network Correlation

Windows and Wireshark provide different types of evidence.

### Host evidence

> What happened on the computer?

Examples:

* Who logged on?
* What process was created?
* Which account was involved?
* What happened locally?

### Network evidence

> What happened between the computer and other devices?

Examples:

* Which IP address was contacted?
* Which protocol was used?
* What DNS query was made?
* Was a TCP connection established?
* Was encrypted communication taking place?

### Why combine them?

A security investigation becomes stronger when host and network evidence are correlated.

For example, Windows might show that a process was created at a particular time, while Wireshark could show that the computer established a network connection around the same time.

Neither source necessarily provides the complete picture on its own.

# 12. Overall Findings

1. Windows Security logs contain multiple types of authentication and process-related events.
2. Event ID 4624 does not automatically indicate that a human user manually logged into the computer.
3. Logon Type is important when interpreting a 4624 event. In the investigated event, Logon Type 5 indicated a service logon.
4. There were no useful Event ID 4625 failed-logon events available during this investigation.
5. Event ID 4688 can provide useful process creation evidence, including process and parent/creator information.
6. A suspicious process path or unusual parent-child process relationship could provide a reason for further investigation.
7. Wireshark allowed DNS, TCP, TLS, and ARP activity to be observed at the packet level.
8. DNS showed the process of resolving a domain name to an IP address.
9. TCP showed the three-way handshake used to establish a connection.
10. TLS showed that application data can be encrypted while network metadata remains observable.
11. ARP demonstrated how local IPv4-to-MAC address resolution takes place.
12. Windows logs and network captures provide complementary evidence and can be correlated during an investigation.

---

# 14. Key Lesson

The main lesson from this investigation is that **an individual event should not automatically be treated as suspicious**.

A SOC investigation requires examining the context around an event, identifying relevant evidence, building a timeline, and correlating information from multiple sources.

Windows Event Viewer provides the **host perspective**, while Wireshark provides the **network perspective**.

Combining both can provide a much clearer picture of what happened.
